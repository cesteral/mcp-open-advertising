# DV360 API v4 → v5 migration: scope and recommendation

Status: scoping only, no source changes. Written 2026-11-25.

## Recommendation

**Wait. Do not migrate to v5 yet; start when Google moves v5 to general availability or announces a v4 deprecation, whichever comes first.** Prepare now only by adding a watch (below).

Why:

1. **v5 is a public beta.** Google's release notes (read 2026-11-25) say "Latest API version: v4" and, on 2026-11-12, "v5 remains in public beta". v5 was released in public beta on 2026-10-22. `apis.list` marks v5 `preferred: true` anyway, so `preferred` is **not** a readiness signal.
2. **v4 has no deprecation or sunset date.** The deprecations page lists v4 (released 2025-03-27) with empty Deprecation and Sunset cells. There is no deadline forcing a move.
3. **The migration is not mechanical.** v5 removes methods we map (top-level `inventorySources` create/patch/get/list) and replaces an enum value (`TARGETING_TYPE_INVENTORY_SOURCE`) that we publish in six tool schemas. Some of this changes what the tools can do, not only how they call Google. A beta can still change before GA, so doing the work now risks doing it twice.
4. **The deadline is predictable once it starts.** The v3 → v4 precedent: v4 beta 2025-02-13, v4 GA 2025-03-27 (6 weeks), v3 deprecation announced 2025-04-02 (6 days after v4 GA), v3 sunset 2025-10-07 (about 6 months later). If v5 follows, GA lands around December 2026 to January 2027, a v4 deprecation notice follows within days, and v4 sunsets roughly mid-2027. That is enough time to migrate after GA, and the pattern is why the watch matters.

This is a prediction from one precedent, not a Google commitment. The v2 → v3 and v1 → v2 rows give 6 to 7 months from deprecation to sunset, which is consistent.

### Methods

### Affected code, by area

**1. The `inventorySource` entity: the one real redesign.**

`STATIC_ENTITY_API_METADATA.inventorySource` (`packages/dv360-mcp/src/mcp-server/tools/utils/entity-mapping-dynamic.ts:175`) maps to top-level `/inventorySources` with `partnerId` or `advertiserId` as query parameters. v5 has no such resource. Deals move to `/partners/{partnerId}/inventorySources` and `/advertisers/{advertiserId}/inventorySources` (path-scoped, read-only get and list, the other scope an optional query parameter), and the list response key becomes `inventorySourceDeals`. Create, patch and edit-accessors disappear, so the entity becomes read-only. IDs also change: Google states cached `InventorySource` IDs are invalid after migration.

Touches:

- `entity-mapping-dynamic.ts:175` (metadata) and `:86` (the `writeScopeInQuery` doc comment, which cites `inventorySources.create/patch`). `writeScopeInQuery` and the `partnerId`/`advertiserId` query handling in `DV360-service.ts:238-273, 600` stop applying to this entity. `inventorySourceGroup` is unchanged in v5 (diff) and keeps them.
- The scope-in-path form needs a new metadata shape: today `apiPathTemplate` is a fixed template with `parentResourceIds`, and a path that depends on which of two ids the caller gave is new. This is the largest design question (see Open decisions).
- `list-entities.tool.ts:76-78` (`scopedQueryParamEntities` set and the "require partnerId or advertiserId" refine) and the matching sentence in `packages/dv360-mcp/CLAUDE.md`.
- `entity-id-extraction.ts:34, 107` (`inventorySourceId`).
- `create-entity`, `update-entity`, `bulk-create-entities`, `bulk-update-entities`: `inventorySource` leaves their `entityType` enums (it becomes `isReadOnly`).
- Tests: `tests/tools/dv360-wire-requests.test.ts:653-690` (the `inventorySource create` wire test, to be deleted), `tests/services/dv360-service.test.ts:324-335` (`getEntity("inventorySource")` URL), `tests/mcp-server/tools/utils/entityApiMetadata.test.ts:59`, and the enum assertions in the `dv360-create-entity`, `dv360-update-entity`, `dv360-list-entities`, `dv360-get-entity` and `dv360-delete-entity` tests that list `inventorySource`.

**2. Targeting types: `TARGETING_TYPE_INVENTORY_SOURCE` is removed.**

`ALL_TARGETING_TYPES` in `targeting-metadata.ts:19` (and the description at `:241` and the category group at `:548`) lists it. v5 replaces it with `TARGETING_TYPE_INVENTORY_SOURCE_DEAL` and `TARGETING_TYPE_AUCTION_PACKAGE` and adds `TARGETING_TYPE_COMBINED_AUDIENCE`, `_CUSTOM_LIST`, `_FIRST_PARTY_AND_PARTNER_AUDIENCE`, `_GOOGLE_AUDIENCE`, `_LOOKALIKE_AUDIENCE` (diff: the v5 `targetingType` parameter text of the assigned-targeting methods). Ad-group audience targeting moves from one `TARGETING_TYPE_AUDIENCE_GROUP` to those five separate types. Line items keep `TARGETING_TYPE_AUDIENCE_GROUP`.

Touches:

- `ALL_TARGETING_TYPES` feeds `create-assigned-targeting`, `delete-assigned-targeting`, `get-assigned-targeting`, `list-assigned-targeting` and `validate-targeting-config`, plus `targeting-types.resource.ts` and `targeting-schema.resource.ts`.
- `TARGETING_TYPES_BY_PARENT` (`targeting-metadata.ts:136`): the ad-group create and delete lists (which hold `TARGETING_TYPE_AUDIENCE_GROUP`) must move to the five audience types, and the advertiser list needs review against v5's per-method text.
- Prompts that name `TARGETING_TYPE_AUDIENCE_GROUP` (`targeting-management.prompt.ts:241`) need a v5 note for ad groups.
- The `AssignedTargetingOption` schema gains six `*Details` fields (diff).

This is the most user-visible change: an agent that targets an ad-group audience via `AUDIENCE_GROUP` today gets a 400 from Google in v5.

**3. Generated schemas (`src/generated/schemas/{types,zod}.ts`), regenerated from v5.**

Diff of the 201-schema closure of our `rootSchemas`:

- Removed: `Adloox` (replaced by `Peer39`, which also changes `ThirdPartyVerifierAssignedTargetingOptionDetails` and the `PartnerCostType` enum), `TargetingExpansionConfig.audienceExpansionLevel` and `.audienceExpansionSeedListExcluded`, `YoutubeAndPartnersSettings.relatedVideoIds` (replaced by `relatedVideos`, new `RelatedVideo` schema).
- Added: `AdGroup.adSource` and `.creativeAssignments`, `AdGroupAd.containsSyntheticMedia` and `.parentCreativeId`, `userSpecifiedTrackingUrl` on `AudioAd`, `CommonInStreamAttribute` and `VideoPerformanceAd`, plus the audience and auction-package details schemas.
- Enum changes on `InsertionOrder.insertionOrderType` (adds `OUT_OF_HOME`), `SdfConfig.version`, `PartnerCost.costType`, `DoubleVerifyFraudInvalidTraffic.avoidedFraudOption`, `DigitalContentLabelAssignedTargetingOptionDetails` and `SensitiveCategoryAssignedTargetingOptionDetails` (the last three drop previously deprecated values).
- v5 lets `adGroupAds` create, patch and delete video performance ads (2026-11-12 note). Our metadata keeps `adGroupAd` `isReadOnly`; enabling writes is a separate enhancement, **not** part of this migration.
- `insertionOrders.list` can return `OUT_OF_HOME` orders in v5. Nothing here branches on `insertionOrderType`, so it should pass through, but `dv360_list_entities` consumers see a new value.

The generator needs `apiVersion` set to `v5` in `config/schema-extraction.config.ts`; the cache filename in `scripts/lib/fetch-discovery.ts` (lines 150, 210) is already version-aware. Rerun the schema-size guard (`tests/schema-size`, `node tests/test-schema-size.cjs`), since the schemas grow.

**4. URL, config and version strings.**

- `src/config/index.ts:33` `dv360ApiBaseUrl` default `…/v4` → `…/v5`.
- `dv360-http-client.ts:57-73`: the upload base derives from the base URL (`/upload/v4`), so uploads follow. Verify `advertisers.assets.upload` and `adAssets.upload` against v5 (same shape per diff).
- `.env.example`, `README.md`, `docs/ARCHITECTURE.md`, `docs/openapi-schema-extraction-spec.md` mention v4.
- About 190 lines with a `v4` literal across 28 test files (76 in `tests/tools/dv360-wire-requests.test.ts`, 29 in `dv360-snapshot-currency-wire.test.ts`, 12 each in `dv360-attach-creative-wire.test.ts` and `entityApiMetadata.test.ts`, and smaller counts elsewhere). Mostly path regexes (`/^\/v4\//`) and `// basis:` comments citing v4 Discovery. The URL part is mechanical; each `// basis:` citation must be re-checked against v5 Discovery, not rewritten blindly (the wire-request-coverage ratchet requires a basis).
- `tests/fixtures/dv360-v4-item-methods.json` (used by `tests/utils/dv360-item-method-params.test.ts`): rename to `dv360-v5-item-methods.json` and re-extract. The `inventorySource` entry changes shape completely (path-scoped, get only). All other entries should be identical bar the version. The provenance block must point at v5.
- Code comments citing v4 Discovery behaviour (`dry-run.ts:252, 439`, `capture-snapshot.ts:128, 264`, several in `entity-mapping-dynamic.ts`, `DV360-service.ts:107, 113`, `create-entity.tool.ts:147-154`) need re-verifying against v5, not just a rename.

**5. Things the diff says do NOT change** (for effort estimates): `campaigns`, `insertionOrders`, `lineItems` (including `duplicate` and `bulkUpdate`), `adGroups`, `creatives`, `advertisers`, `partners`, `customBiddingAlgorithms` (with rules, scripts, `uploadRules`, `uploadScript`), `inventorySourceGroups`, `locationLists`, the assigned-targeting CRUD methods (apart from the targeting-type values above) and the upload methods. `attach-creative`, `get-ad-preview`, `get-delivery-estimate`, `get-pacing-status`, `adjust-line-item-bids`, `bulk-update-status` and `upload-image`/`upload-video` depend only on those and need only the version string in their tests.

There is **no audience tool** in this package: no `firstPartyAndPartnerAudiences`, `lookalikeAudiences` or Customer Match call exists in `src/`, so the Customer Match removal costs us nothing. Audience impact is limited to targeting types (area 2) and the generated schemas (area 3).

## Hashes and the governed-write contract

- `scripts/lib/tool-definition-hashes.snapshot.json` holds 28 dv360 hashes. The tools whose published schema embeds `ALL_TARGETING_TYPES` or the entity-type lists change hash: I count **about 9 of the 28** (4 create/update, 4 assigned-targeting, `validate_targeting_config`), plus `get_entity`/`list_entities`/`validate_entity` if the entity list changes. The exact set comes from regenerating (`pnpm sync:tool-definition-hashes` after a build). A hash that moves for a tool this migration did not intend to change means regenerating the schemas moved something upstream (CLAUDE.md note).
- Of the 17 tool files that carry `annotations.cesteral`, those with hash changes get their `verification` status demoted automatically (`docs/architecture/release-attestation.md`). Governance must admit the new hashes before an `enforce` posture accepts them; the precedents are the 12-hash admission for LinkedIn (#210) and the `parents` rollout (contract 2.3.0). This is a **coordination cost with the governance repo**, and the main reason to ship everything in one hash move rather than piecemeal.
- The contract snapshots (`NormalizedEntitySnapshot`, `parents`, `readPartnerSnapshotShape`) are built from `Campaign`, `InsertionOrder`, `LineItem` and `Advertiser` fields. The diff shows none of the fields the builders read changing (`budget`, `entityStatus`, `pacing`). So I expect **no contract version bump**, but confirm by running `tests/tools/dv360-snapshot-*.test.ts` against the regenerated schemas. If a snapshot field list includes `partnerCosts.costType`, Adloox → Peer39 reaches the contract.
- Dry-run rules in `dry-run.ts` cite v4 Discovery text (DRAFT-only create status, archive-before-delete). The diff found no change in substance for `insertionOrders.create`, `lineItems.create` or the delete methods, but description text differs across about 100 methods (mostly path strings), so confirm those by reading the v5 text for those methods.

## Weekly watch (proposed addition to `.github/workflows/codegen-drift.yml`)

`apis.list` `preferred` is already `v5`, so alerting on it would fire immediately and carry no information. Watch the signals that mean "start migrating":

1. **v5 GA:** the release notes header "Latest API version" differs from our pinned version.
2. **v4 deprecation:** the deprecations page row for our pinned version has a non-empty Deprecation date.

Proposal: a small `scripts/check/check-dv360-api-version-watch.mjs` beside `check-dv360-codegen-drift.mjs`, run as a second step or job in the same workflow, with the same exit codes (0 ok, 1 signal, 2 could not check). It reads the pinned version from `dv360ApiBaseUrl` in `src/config/index.ts`, fetches the two vendor pages and extracts the two values. It also logs, as information only, which version `apis.list` marks `preferred`, and fails if the pinned version disappears from `apis.list` (a sunset signal). Scraping HTML is brittle, but a layout change then surfaces as exit 2 ("could not check"), which the existing workflow already distinguishes from drift, so a broken parse is visible rather than silent. Keep it non-PR-blocking, for the reason the existing job gives.

This is a proposal only; nothing has been added to the workflow.

## Migration steps (when triggered)

1. Settle the open decisions below and write them into the PR description.
2. Set `apiVersion` to `v5` in `config/schema-extraction.config.ts`, regenerate `src/generated/schemas`, and review the diff against area 3. Keep the revision pin from #411 in step.
3. Re-extract the item-methods fixture (rename to v5) and update `entityApiMetadata` expectations.
4. Rework `inventorySource` (area 1): new metadata shape, read-only, list key `inventorySourceDeals`, delete the create wire test.
5. Update `ALL_TARGETING_TYPES`, descriptions, categories and `TARGETING_TYPES_BY_PARENT` (area 2); update prompts.
6. Bump `dv360ApiBaseUrl`; update tests; re-verify each `// basis:` and each v4-citing code comment against v5 Discovery.
7. Build, `pnpm sync:tool-definition-hashes`, `pnpm run generate:manifests`; list which hashes moved and confirm each is expected. Rerun the routing evals.
8. Update `platform-facts.json`, the verification flow, `README`/`.env.example`/docs and `packages/dv360-mcp/CLAUDE.md` (the `inventorySource` sentence and the v4 references).
9. Coordinate the new hashes with the governance repo before the connector version goes through `enforce`.
10. Rely on CI for the full matrix; deploy to the single dev environment and run the live checks below.

Live checks (wire tests only prove what we send, not what Google accepts): get and list an inventory source deal under an advertiser scope and under a partner scope and confirm the IDs differ from v4; create an ad-group audience assignment with one of the five new types; list an advertiser that has an Out-of-Home insertion order; one asset upload.

## Risks

- **Beta churn.** Google can still change v5 before GA; the 2026-11-12 note shows it still gains features. Migrating early means repeating the regenerate-and-review step and the hash move.
- **Silent targeting break.** `TARGETING_TYPE_AUDIENCE_GROUP` on an ad group and `TARGETING_TYPE_INVENTORY_SOURCE` become invalid. Clients and prompts that hard-code them get a 400, so prompts change in the same PR.
- **Cached inventory-source IDs become invalid** (Google). We hold no state (CLAUDE.md principle 2), but agents and users may hold v4 deal IDs.
- **Hash and governance coordination.** About 9 tools change hash in one step; each governed one needs admission. Splitting the migration multiplies this.
- **A capability goes away.** v5 removes inventory-source creation and editing, which `dv360_create_entity` and `dv360_update_entity` offer today. Under the no-backward-compat rule that means deleting it, not keeping a v4 path. A mixed v4/v5 client for one entity is out of scope.
- **Upstream document risk is unchanged:** the generator reads Google's live Discovery document (`packages/dv360-mcp/CLAUDE.md`, #79), and a beta document can move under us more than a GA one.

## Open decisions for the migration PR

1. How to model path-scoped `inventorySource` (`/advertisers/{id}/inventorySources` vs `/partners/{id}/inventorySources`): a new `EntityApiMetadata` option where the scope chooses the path, or two entity types (`advertiserInventorySource`, `partnerInventorySource`). The first keeps one agent-facing name and a smaller hash change; the second mirrors Google's model but adds enum values.
2. Whether to also expose auction-package retrieval (`targetingTypes.targetingOptions`, not called today), which agents need to find auction-package IDs for `TARGETING_TYPE_AUCTION_PACKAGE`.
3. Whether ad-group audience targeting needs a helper (one call per audience type) or only a prompt update.
4. Whether to admit the hashes with governance in one release or two.
