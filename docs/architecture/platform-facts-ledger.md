# Platform-Facts Ledger

Reference for this subsystem. [CLAUDE.md](../../CLAUDE.md) keeps a short summary and links here.

`platform-facts.json` records every load-bearing claim this repo makes about an external platform it does not own — 73 facts: the 15 versioned and unversioned API base URLs (dbm-mcp's is the googleapis client's `version: "v2"` selector), the LinkedIn `YYYYMM` header pin, 44 behavioural constraints (the ones in the per-package `CLAUDE.md` files, the LinkedIn `/v2/` → `/rest/` endpoint claims from #210, three verified Snapchat reporting/create claims from #233, three verified TikTok async-report claims from #232, three verified TikTok Upgraded Smart+ claims (the 2027-01-01 legacy create cutoff, the Smart+ objectives, and the id and update differences), three verified TTD bulk-operation claims from #231, twenty-two verified LinkedIn claims read from its docs (version, analytics, pagination, account scoping, protocol header, rate limits, and from #210's targeting PR the facet and value URN namespaces, the adTargetingEntities finders, the targetingCriteria shape, forecasts, audience counts and ad previews, and from #301 the conversion-rule `account` finder), Meta's reported all-version v26 changes and the v26 field schema meta-mcp's default reads are checked against, from #229, and the Amazon DSP Unified API entity surface and its gaps from #234), and each server's default rate limit (13 `<platform>.rate_limit_default` facts, pinned to the `default(N)` literal so a default cannot be raised without touching its fact). No platform quota could be sourced from a primary document, so every default was kept and the snippet-level figures are recorded as `unverified` — confirm them on the vendor page before raising a default. Each entry carries the claim, the source URL, where the code relies on it, and when it was last checked (#202).

Two of these have already rotted. `linkedin-mcp` pinned `LinkedIn-Version: 202409` for roughly a year past sunset with every call erroring and nothing detecting it (#206/#209); Google's v4 Discovery rev 20260608 removed campaign + insertion-order assigned targeting and broke all CI (PR #79). One was caught loudly, the other was silent for a year, and the difference was luck about which fact happened to be fetched at build time.

**Two modes, because they have different failure politics:**

| Mode                                                   | Where                                                           | What it does                                                                                                                                                                   |
| ------------------------------------------------------ | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `pnpm check:platform-facts`                            | **CI, PR-blocking**                                             | Hermetic. Ledger shape, plus every `codeRef` still existing _and still containing the value the ledger claims_. Can only fail because of something in the commit under review. |
| `check-platform-facts.mjs --freshness --due-within 30` | **Scheduled** (`.github/workflows/platform-facts.yml`, Mondays) | Time-dependent. Reports expired facts, and facts due within 30 days, and opens/updates a tracking issue.                                                                       |
| `check-platform-facts.mjs --freshness`                 | **Fleet release** (`release.yml`, first step of the `v*` lane)  | Same check, as a gate: a stale load-bearing fact fails the release before anything is built or published.                                                                      |

The freshness half is deliberately **not** PR-blocking, for the same reason as `check-terraform-drift.mjs`: it would turn `main` red by the passage of the calendar, on a commit that changed nothing. It **does** block a fleet release, because a `v*` tag claims the servers work against their platforms today. The contract-library lane is exempt, since neither library relies on a platform fact. To release past an expired fact, re-verify it, or mark it `superseded` / move its deadline in a reviewed commit that says why. Being unable to check is not a reason. The release job checks out the **tagged** commit, so unblocking needs that commit on `main` and a fresh tag.

**A moved deadline is capped at one cadence from today** (`REFRESH_DAYS`: 90 days for versioned base URLs and the LinkedIn version header; 180 for unversioned base URLs, behavioural constraints and auth requirements). A `verifyBy` further out is reported as `DEADLINE PARKED` and fails the release like an expired fact. Without the cap the escape hatch would accept `2099-01-01` as readily as a real extension. The weekly job's 30-day warning exists so the first alert does not land the same week releases start failing.

**The hermetic half is the one with teeth today.** Bumping a pinned version without updating the ledger fails CI with the file, line, and both values — verified by actually editing `gads-mcp`'s config from `v23` to `v24` and watching it fail.

**Nearly every fact ships `status: "unverified"` with `verifiedAt: null` and a `verifyBy` deadline.** This is the honest state, not an oversight: the vendor doc hosts (`learn.microsoft.com` among them) were unreachable from the sandbox the fleet review ran in, so nobody had read a supported-version table. The exceptions are facts verified from the vendor's own pages: thirteen `linkedin.*` facts read from `learn.microsoft.com` on 2026-10-01 (see `packages/linkedin-mcp/CLAUDE.md`), and nine behavioural ones: three `snapchat.*` (`stats_report_dimension`, `stats_day_bounds_account_timezone`, `campaign_objective_v2`; #233) and three `tiktok.async_*` (`async_report_download_endpoint`, `async_task_statuses`, `async_report_create_options`; #232), both 2026-09-30, and three `ttd.bulk_*` (`bulk_mutation_variable_binding`, `bulk_job_poll_fields`, `bulk_mutation_limits`; #231), 2026-10-01. The doc hosts are reachable from a developer machine even where they were not from the review sandbox, so a fact can be verified by reading the page itself, not a search summary or an SDK spec of it: a summary wrongly called Snap's `report_dimension` response-only, and TikTok's SDK spec omitted a download endpoint and a status enum its docs define (Snap's and LinkedIn's are static HTML that `curl` reads, and LinkedIn's table of contents is `…/linkedin/marketing/toc.json`; TikTok's and TTD's are rendered client-side, so use a real browser, and TTD's code samples are Monaco editors whose text is only in `window.monaco.editor.getModels()`). **An expired fact is not current, and being unable to check it does not make it fresh** — so `unverified` is reported, never silently passed. `verified` requires a `verifiedAt`, and `unverified` forbids one, so the two can never disagree.

**`verifiedAt` must be the date someone actually re-checked.** Never backdate it to when the code was written — that reproduces exactly the false confidence this removes.

**Related: `LINKEDIN_API_VERSION_VERIFICATION_BASIS`.** #209 shipped `LINKEDIN_API_VERSION_VERIFIED_AT = "2026-09-16"` under a docstring reading "when a human last confirmed... against LinkedIn's published list". No such confirmation happened — the list is behind the blocked host, and the `202608` pin was inferred from LinkedIn's documented monthly cadence and one-year window. The basis is now explicit and set to `inferred`, the ledger carries the fact as `unverified`, and a test asserts the two agree. A date with no basis beside it reads as a confirmation that never happened.
