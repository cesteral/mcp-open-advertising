# _cross-fleet review (horizontal consistency across all 13 MCP servers)

## Summary

Scope: Part A only (no vendor-doc fetching). Method: `pnpm install` + `pnpm run build` (writes only gitignored `node_modules/` and `dist/`; `git status` stays clean). I then booted every server in-process with the repo's own `scripts/lib/boot-server.mjs` and read the raw wire `tools/list`, `prompts/list`, `resources/list` and `resources/templates/list`. That gives 314 tools, the same as CLAUDE.md. I also read source. Existing checks all pass: `check:doc-tool-counts`, `check:registry-tools`, `check:registry`, `check:registry-runtime`, `check:platform-facts` (28 facts, all unverified), `check:account-scope`, and `pnpm test:scripts` (426/426). So everything below is drift those ratchets do not cover.

Overall: the fleet follows its structure conventions closely. The same tool file layout is used everywhere, every server calls `bootstrapMcpServer({tools: allTools})`, every tool name has its platform prefix, and every tool declares all 4 MCP hints. The inconsistencies are in behaviour and metadata. Top issues:
1. **Report download sends the user's token to any host the caller names.** In cm360 and sa360, `download_report` attaches the user's Google OAuth Bearer token to a caller-supplied URL with no host allowlist. In 5 more servers it fetches any URL without auth (SSRF). TTD's allowlist admits all of `*.amazonaws.com`.
2. **The shared RateLimiter throws instead of waiting.** Combined with 3-token writes and per-item loops, a bulk tool can only apply about 3 to 6 items per minute on 7 servers. The rest of the batch fails, leaving the platform half-applied. cm360's limiter never enforces anything (key `"cm360"` does not match the pattern `cm360:*`, verified by running it), and neither do sa360's v2 keys. The server card still publishes a cm360 limit.
3. **Irreversible statuses are not declared terminal.** `bulk_update_status` and `update_entity` accept statuses that cannot be undone (REMOVED, Archived, DELETE, Deleted, CANCELED, PERMANENTLY_ARCHIVED, ARCHIVED) on 9 servers. None of these are declared in `registry.json` `terminalOperations`; only dv360 does it right. In two cases the tool's own description says the status "cannot be un-removed" or "cannot be un-archived".
4. **Three tools advertise an empty `inputSchema`:** `msads_get_entity`, `msads_update_entity` and `dv360_duplicate_entity`, because their top-level `discriminatedUnion` is not flattened. Two of them are governed writes, so their `definitionHash` covers an empty schema.
5. **gads splits its governance namespace:** 7 `google_ads.*` contractIds and 3 `gads.*`.

Doc reachability: not applicable (Part B skipped per instructions). Anything below about platform semantics (for example whether a given platform's ARCHIVED is reversible) is marked model-knowledge.
