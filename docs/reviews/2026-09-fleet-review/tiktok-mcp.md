# tiktok-mcp review

## Summary

The package follows fleet conventions well: 25 tools are all registered, prefixed and annotated; governance blocks are complete; dry-run and snapshot plumbing is present; session, retry and rate-limiter wiring are standard. Its accuracy against the TikTok API is poor, though. Several problems would stop the package working against a real account, and nothing has ever been exercised live (there is no `verification.json`, and tests only assert against self-authored mocks).

The live doc hosts could not be reached. `business-api.tiktok.com`, `ads.tiktok.com`, `postman.com` and `soku.ai` all returned an EGRESS_BLOCKED or CONNECT 403. The main evidence is TikTok's own official SDK repo (`github.com/tiktok/tiktok-business-api-sdk`, commit f809c39 of 2026-02-28, PyPI 1.1.3 of 2026-02-27). Its 202 OpenAPI yml files and its Python, JS and Java clients are vendor-authored, and I treated them as close to docs. Everything past Feb 2026 is UNVERIFIED.

**Top 3 issues:**
1. **Wrong upstream auth header.** Every outbound call, including the `validate()` fast-fail, sends `Authorization: Bearer <token>`. All three official SDKs and every spec send the token as an `Access-Token` header and configure no Bearer auth. If TikTok does not also accept Bearer (I could not check this), no session can be established in any auth mode.
2. **The async reporting chain probably never completes.**
   - `report/task/create` is sent without `data_level`/`service_type`/`output_format`.
   - The poller waits for `status === "DONE"` plus a `download_url`.
   - The official SDK spec exposes no `download_url`. TikTok's pattern, and a third-party wrapper, download through `report/task/download/?task_id=`.
   - `fromTikTokStatus` maps every unknown status to `pending`, so if TikTok's status strings differ, `get_report` times out and `check_report_status` reports "pending" forever.
3. **Several endpoints or payloads are wrong against the vendor spec:**
   - `advertiser/info/` without the required `advertiser_ids`.
   - `tool/targeting/search/` sent `keyword`/`scene` where the spec requires `keywords[]`/`search_type`.
   - Image and video uploads missing the required MD5 `image_signature`/`video_signature`.
   - The refresh-token flow posts `grant_type=refresh_token` to `oauth2/access_token/`, whose body requires `auth_code`.
   - The delete, copy, `creative/adcreative/*`, `audience/estimate/` and `ad/preview/` paths do not appear in the vendor SDK (see the inventory).

**Also notable:** `tiktok_bulk_update_status` (`DELETE`) and `tiktok_update_entity` (`operation_status: DELETE`) are irreversible, but only `tiktok_delete_entity` is declared terminal. dv360 declares its analogous tools terminal.

**Pinned version:** `v1.3`. The official SDK (Feb 2026) uses only `/open_api/v1.3/` (1,644 path references, no other version), so as far as I can see v1.3 is current. I found no sunset notice, but that is UNVERIFIED for Mar–Sep 2026.

What the official SDK confirmed:
- The `Access-Token` header is required on all 202 specs. Python `header_params['Access-Token']`, JS `'Access-Token': Access_Token` with `authNames=[]`, Java `localVarHeaderParams.put("Access-Token", …)`.
- Only v1.3 paths appear.
- Request schemas for `report/task/create`, `report/integrated/get`, `report/task/check`, `advertiser/info`, `tool/targeting/search`, `tool/targeting/list`, `tool/region`, `file/image/ad/upload`, `file/video/ad/upload`, `oauth2/access_token`, and the campaign/adgroup/ad create, update and status bodies.

## Open questions

1. Does TikTok's gateway accept `Authorization: Bearer` as an alias for `Access-Token`? If it does, #1 drops to a convention fix. If not, the package has never worked end-to-end, which fits the absence of any live-verification evidence. A single sandbox or live `GET user/info/` settles it.
2. What are the exact `report/task/check` status strings, and does the response include any URL field? The spec output only maps `status`.
3. Do the `*/delete/`, `*/copy/`, `creative/adcreative/*`, `audience/estimate/` and `ad/preview/` endpoints exist in v1.3 at all, perhaps as undocumented aliases? The official SDK is a subset, so its silence is strong evidence but not proof.
4. Is there any refresh flow for Marketing API advertiser tokens (as opposed to creator `tt_user` tokens)? If not, `TikTokRefreshTokenAdapter` and the `X-TikTok-App-*`/`X-TikTok-Refresh-Token` headers should be removed rather than fixed.
5. Has v1.3 been superseded or given a sunset date since Feb 2026? The official SDK (1.1.3, 2026-02-27) still targets only v1.3, and I could not read the changelog page (docs id 1740579480076290) through the proxy.
6. What are TikTok's return codes? We need the official appendix to validate the `AUTH_ERROR_CODES`/`RATE_LIMIT_CODES` sets (#21).
7. The CLAUDE.md note "tiktok-mcp: `X-TikTok-Advertiser-Id` header in HTTP mode; image/video upload supported" is accurate as a description of the code: the header is required in `tiktok-bearer` mode (`tiktok-auth-adapter.ts:267-277`), and it is part of the credential fingerprint. "Upload supported" is optimistic given #6.
