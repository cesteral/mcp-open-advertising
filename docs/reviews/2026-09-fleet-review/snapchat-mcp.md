# snapchat-mcp review

## Summary

The package is well structured. All 25 tools are registered in `allTools`, every tool name carries the `snapchat_` prefix, governance blocks are present, the session-services and auth-adapter patterns match the fleet, and `validate()` fails fast via `GET /v1/me`. It has several functional defects on the main code paths, though:

1. **The rate limiter makes the bulk tools unusable at their advertised sizes.** The default is 10 requests/min and each write consumes 3 tokens, so with the default config:
   - `delete_entity` (max 20) fails from the 4th id.
   - `bulk_update_*` (max 20/50) rejects the whole batch past about 7 items.
   - `adjust_bids` (max 50) fails after 2.

   Snap's documented limit is 10 req/s per token.
2. **Reporting is broken in three ways:**
   - Breakdowns are appended to `fields` instead of being sent as `report_dimension`.
   - `datePreset` produces `…T00:00:00Z` / `…T23:59:59Z`. Snap requires ad-account-timezone day boundaries for the default `DAY` granularity.
   - `includeComputedMetrics` treats micro-currency `spend` as currency, so CPA/CPM/CPC come out 1,000,000× too high.
3. **Create does not inject the parent IDs** (`ad_account_id`, `campaign_id`, `ad_squad_id`), even though the descriptions say it does. `duplicate_entity` actively strips `ad_account_id`.

Documentation drift is also serious:
- The `reporting-reference://snapchat` resource and the bulk-operations prompt are copies of the TikTok ones.
- Schemas, examples and prompts still tell agents to set campaign `objective` (Snap says it rejects this on create from 2025) and a required `placement` (Snap says it cannot be set since June 2020).
- The package README misstates the rate limit, the status enum and the API version.

**Doc reachability:** every official Snap host (`developers.snap.com`, `marketingapi.snapchat.com`, `businesshelp.snapchat.com`) is blocked by the egress proxy (EGRESS_BLOCKED). All "live-doc" evidence below comes from **search-engine summaries of developers.snap.com pages** (WebSearch), not from fetched pages. I label it "search-snippet". Treat it as strong corroboration, not a first-hand read.

## Part B notes

- **API version / base URL:** Snap has a single unversioned `v1` path on `https://adsapi.snapchat.com`, with no version header and no sunset schedule to pin. The deprecation process runs through the Breaking Changes Log: 90 days to sunset, then end of life two weeks later (search-snippet). `platform-facts.json` `snapchat.api_base` (unverified, verifyBy 2026-12-15, codeRef `config/index.ts:26`) is consistent with the code. It records no field-level facts, although field-level deprecations (`objective`, `placement`) are what actually break this package.
- **CLAUDE.md "Server-Specific Notes":** "Ad Squads (adGroups), cursor-based pagination" is accurate: `paging.next_link` is followed verbatim.
- **Micro-currency:** writes are correct (`bid_micro = round(price*1e6)`, and the descriptions say "multiply by 1,000,000"). Reads and computed metrics are wrong (#5).
- **OAuth refresh:** the endpoint, grant type and form encoding match the docs (search-snippet). Refresh-token rotation is handled by `OAuth2RefreshAdapterBase`. Snap says refresh tokens do not expire.
- **Bulk delete semantics:** Snap has no bulk-delete endpoint, so the per-id DELETE is correct, and deletes are irreversible (search-snippet). `registry.json` declares `snapchat_delete_entity` terminal. The description text is stale (#12).
- **New capabilities not covered (low priority):** `objective_v2_properties`, `placement_v2` (including the CHAT_FEED+FEED bundling from 2026-05-06), multi-country targeting, chunked media upload, audit/change logs, custom audience segments, pixels/Conversions API, lead-gen forms, catalogs/DPA, Reach & Frequency, and campaign/ad-squad stats endpoints (only ad-account stats with `breakdown` are used).
