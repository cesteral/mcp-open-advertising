# linkedin-mcp review

## Summary

**Overall health: poor for live use. The structure is fine, but most of the wire formats are wrong.** The package follows the fleet's conventions: all tools are prefixed, every tool is registered, governance blocks are present and `delete_entity` is declared terminal. The `LinkedIn-Version` pin is also defensible. `202608` looks like an active release (search results mention its release notes), but it is **not the latest**, because `202609` exists. However, almost every data-plane call would fail against the real API, for three reasons:

1. **`/rest/adAnalytics` is sent in Rest.li 1.0 query syntax with the Rest.li 2.0 protocol header** (`accounts[0]=…`, `dateRange.start.year=…`). On top of that, `LinkedInHttpClient.buildUrl` uses `URLSearchParams`, which percent-encodes Rest.li 2.0's structural characters `( ) : ,`. So the client *cannot* express a valid 2.0 query even once the parameter names are fixed. As a result, both analytics tools and the analytics resource are broken. The default metric `conversions` is probably not a valid field, and `MEMBER_COUNTRY`/`MEMBER_REGION` were removed in 2020.
2. **Every call still on `/v2/` (11 call shapes, listed below) targets a surface that appears to have been sunset.** Search results say legacy unversioned Marketing `/v2/` was sunset around 2023-06-30. The legacy resource names also carried a `V2` suffix (`adCampaignsV2`, `adCreativesV2`) and were keyed by numeric id. The code's `/v2/adCampaigns/{urn-encoded}` paths therefore look wrong even for the legacy surface. This covers get/update/delete for campaigns, campaign groups, creatives and conversions, plus all creative/conversion list/create, `duplicate_entity`, `adjust_bids`, `bulk_*`, forecasts, previews and both uploads.
3. **The targeting tools and resource use facet names, finders and URN namespaces that do not match LinkedIn's.** Examples: `q=type`/`q=account` on `/rest/adTargetingFacets`, `MEMBER_INTERESTS`/`GEO` as facet types, and `urn:li:adTargetingFacet:geos`/`memberSeniorities`/`companySizes`, `urn:li:adSeniority:5`. Value lookup belongs on `/rest/adTargetingEntities` (`q=adTargetingFacet` / `q=typeahead`).

**Doc reachability:** `learn.microsoft.com`, `api.linkedin.com`, `www.linkedin.com` and `developer.linkedin.com` are all **EGRESS_BLOCKED** (proxy 403 on CONNECT). The `MicrosoftDocs/linkedin-api-docs` repo was not found or not accessible through add_repo, and `github.com` is session-bound. **No official page could be fetched live.** Every "accuracy" finding below is based on one of two things, and none is `live-doc`:
- **Search results:** WebSearch snippets of learn.microsoft.com pages. These were summarized by the search tool, and the index lists pages with `view=li-lms-2026-09`.
- **Model knowledge:** my own knowledge, labelled as such.

Headers: every request sends `Authorization: Bearer`, `LinkedIn-Version: <pin>` and `X-Restli-Protocol-Version: 2.0.0` (linkedin-http-client.ts:225-229; auth validate at linkedin-auth-adapter.ts:48-52). The 2.0.0 header is correct for the versioned API (Ad Preview and Conversions docs, search results). The query-string syntax does not match it (finding 1). The PUT to the upload URL also sends the Rest.li and version headers, which is harmless. Partial update is `POST` with `X-Restli-Method: PARTIAL_UPDATE` and `{patch:{$set}}` (linkedin-http-client.ts:98-110), which is correct per Rest.li (model knowledge). URN path encoding with `encodeURIComponent` is correct for a *path key* where a URN is the key (creatives). It is wrong where the key is numeric (adAccounts, campaigns, campaign groups).

## Consistency checks that passed (brief)

- **Tool structure:** every `*.tool.ts` exports its schema, metadata and logic, and all 21 are registered in `allTools` along with `linkedin_search_tools`. There are no orphaned files.
- **Naming:** every tool is prefixed `linkedin_` with fleet-standard suffixes. The fleet has no `submit_report` for LinkedIn because analytics is synchronous, which is fine.
- **Registry:** `registry.json` lists all 22 tools and 3 auth modes. `linkedin_delete_entity` is declared terminal, and `reversible-operations-allowlist.json` is empty.
- **Config:** `config/index.ts` auth modes are `linkedin-bearer | jwt | none`, which matches the registry.
- **Wiring:** the retry config and rate limiter go through the shared `executeWithRetry` and `createPlatformRateLimiter`, and the session-services pattern is followed. No `verification.json` exists, so all tools are `declared`, which is correct.
