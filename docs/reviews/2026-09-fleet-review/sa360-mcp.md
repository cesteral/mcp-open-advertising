# sa360-mcp review

## Summary
Overall the package is well structured: 17 registered tools, governance annotations on all 3 writes, shared transport, session services and retry are all wired. Its correctness against the pinned API is poor, though. The code was evidently written against Google Ads GAQL field names, and several default queries reference fields and resources that **do not exist in SA360 Reporting API v0**. As a result `sa360_list_entities`/`sa360_get_entity` fail for 3 of 8 entity types, and `sa360_get_change_history` fails outright. Checked against the live v0 discovery schema. The offline-conversion write tools send fields that are not in the v2 `Conversion` schema (`gclid`, `floodlightActivityId`) and cannot send the `conversionId` the API requires. `sa360_download_report` forwards the user's Google bearer token to any caller-supplied URL.

**Top 3 issues:**
1. v0-invalid fields: `ad_group.campaign`, `ad_group_ad.ad_group`, `campaign_criterion.campaign` and the whole `change_event` resource. These break list/get for adGroup, adGroupAd and campaignCriterion, plus the change-history tool.
2. Conversion upload payload does not match the v2 `Conversion` schema: no `conversionId` on insert, and non-existent `gclid`/`floodlightActivityId` fields.
3. A token leak and SSRF in `download_report`, because `downloadUrl` is accepted without a host check.

**Accuracy vs. the platform:** Google's discovery directory now publishes `searchads360:v23` with `"preferred": true`. It has about 80 `:mutate` methods, including `campaigns:mutate`, `adGroups:mutate` and `adGroupAds:mutate`, plus `:uploadClickConversions`. So the ledger claim that v0 is current is stale. The "read-only / no mutate" claim is true for v0 only.

**Doc reachability:** `developers.google.com`, `ads-developers.googleblog.com` and `groups.google.com` are all EGRESS_BLOCKED, so no release notes or reference pages could be read. The machine-readable **Google discovery documents were reachable** and were used as the live source of truth: v0 rev 20260820, v23 rev 20260820, doubleclicksearch v2 rev 20260921. Unauthenticated probes of v0/v23/v2 endpoints return 401, which confirms they are routed.

**Checked and correct:**
- Pagination uses `pageToken`/`nextPageToken`, consistent with gads.
- v0 base URL and paths: search, listAccessibleCustomers, customColumns and searchAds360Fields:search all exist in v0 with the correct HTTP methods.
- `login-customer-id` header on v0 only.
- OAuth scope `https://www.googleapis.com/auth/doubleclicksearch` matches both discovery docs.
- Token endpoint is `oauth2.googleapis.com/token`.
- The v2 conversion body `kind: doubleclicksearch#conversionList` and POST insert / PUT update are correct.
- `state` enum ACTIVE/REMOVED matches the schema (DELETED is deprecated).
- `type` ACTION/TRANSACTION, `revenueMicros` (value × 1,000,000), `quantityMillis` and `conversionTimestamp` in epoch millis UTC all match.
- `customMetric.value` is a number and `customDimension.value` a string, as in the schema.
- All `segments.*`/`metrics.*` fields used by get_insights and get_insights_breakdowns exist in v0.
- The governance annotations (effect class, dry_run excluded) are internally consistent, and `terminalOperations: []` is defensible: a REMOVED conversion can be set back to ACTIVE, per model knowledge.

## Open questions
1. Is `searchads360` v23 generally available, and has Google announced a v0 sunset date? The discovery directory marks v23 preferred, but the release notes are behind the blocked `developers.google.com`. This decides whether #7 is a medium or a high.
2. Does the legacy v2 `reports.request` still return data for advertisers fully migrated to the new SA360 experience, and is `customerId` now required on v2 conversions for them? Unanswerable without the docs or a live account.
3. Does v2 reject unknown JSON fields (`gclid`, `floodlightActivityId`) with a 400, or silently ignore them? Either way the rows lack a click ID or segmentation (#5), but the failure mode affects how `summarizeConversionOutcome` reports it.
4. Is the 200-rows-per-request conversion limit still correct? (#20)
5. Should `CLAUDE.md`/`platform-facts.json` split `sa360.reporting_api_is_read_only` into "v0 has no mutate" (true) and "SA360 API has no mutate" (false as of v23)?
6. The v0 discovery schemas are the only live evidence for #1, #2 and #9. The repo's own `src/generated/openapi.json` agrees with them, but a single live `searchAds360Fields:search` call per field would settle it definitively.
