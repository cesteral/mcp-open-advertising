# amazon-dsp-mcp review

## Summary

Structurally the package is in good shape. 27 business tools plus `amazon_dsp_search_tools` are all registered. The README's count of 28 is correct. Every write carries a `cesteral` block, and account-scope checks are applied consistently. **The upstream API surface is the problem.**

1. **The entity-management half (`/dsp/orders`, `/dsp/lineItems`, `/dsp/creatives`, `/dsp/targets`, `/dsp/creativeAssociations`, `/dsp/advertisers`) targets an API that Amazon's own current material no longer documents.**
   - Amazon's official migration guide (amzn/ads-advanced-tools-docs, commit of 2026-09-22) treats `/dsp/v1/campaigns|adGroups|adCreatives|targets` as the *legacy* API to migrate from, and maps it to the Unified `/adsApi/v1/{create,update,query,delete}/...`.
   - `/dsp/orders` is a generation older than that "legacy" API.
   - None of these endpoints appears in Amazon's current Postman collection.
   - No write on this path has ever succeeded live.
2. **The Ads API v1 half (commitments and forecasts) sends the wrong headers.**
   - Amazon's spec, including the package's own committed `src/generated/v1/types.ts`, requires `Amazon-Ads-ClientId` on every v1 call. `retrieve/campaignForecasts/dsp` additionally requires `Amazon-Ads-AccountId`.
   - The HTTP client sends only `Amazon-Advertising-API-ClientId` and `Amazon-Advertising-API-Scope`.
3. **The reporting contract contradicts Amazon's collection and the repo's own docs.**
   - The code calls un-scoped `/dsp/reports`, with `YYYYMMDD` dates and metrics joined into one string.
   - Amazon's official Postman collection calls `/accounts/{dspAccountId}/dsp/reports`, with `YYYY-MM-DD` dates, a metrics array and `vnd.dspcreatereports.v3` / `vnd.dspgetreports.v3` Accept headers.
   - CLAUDE.md says the same as Postman. The package README and the entity-hierarchy resource describe a third contract, Sponsored Ads v3 `/reporting/reports`.

Other issues:
- The jwt/none static-token session path drops the ClientId. This is the same bug as live-test finding #1, reintroduced on a different code path.
- A single process-wide base URL means a hosted server can serve only one region (NA, EU or FE).
- `download_report` fetches any URL. The TTD server has a host allowlist for this; this server does not.
- `bulk_update_status` can archive entities, which the server itself calls unrecoverable, yet it is not declared terminal.

**Doc reachability:**
- `advertising.amazon.com` is **egress-blocked**, as are `help.funnel.io` and `api.github.com`.
- **The official Amazon repo `github.com/amzn/ads-advanced-tools-docs` could be git-cloned** (HEAD `677d3b4`, 2026-09-22). It contains the Postman collections, the Unified DSP OpenAPI spec (`unified-api-dsp.json`) and the DSP migration guide. Every "live-doc" claim below cites that repo.
- Release notes, the deprecations page and any sunset dates were **not** reachable. No sunset date for `/dsp/orders` could be confirmed.

### On the deliberate omission of 429 from `isAmazonDspRetryable`

- **Code is correct and consistent.** `http-client.ts:32-34` returns `status >= 500`, and `maxRetries: 2`. The transport publishes the real predicate on the server card (`streamable-http-transport.ts:63-66`), so the card shows `retryOnStatus` without 429 and `resendSafeForAllMethods: []`, which matches the CLAUDE.md table. The shared layer still blocks 5xx resends on POST.
- **The justification is empirical, not documented.** It rests on "no Retry-After, multi-hour penalty window", observed on EU `/dsp/orders` on 2026-05-15. I could not reach Amazon's rate-limit or throttling documentation. From model knowledge, not verified: Amazon's general guidance recommends exponential backoff on 429 and says some APIs return `Retry-After`. The omission is defensible for the legacy `/dsp/*` surface. It may be over-conservative for `/adsApi/v1/*`, which is a separate throttling domain.
- **Recommendation:** keep the omission, record it in platform-facts as `unverified`, and consider honouring `Retry-After` when the header is present.

### LwA refresh flow

- The flow is correct as coded: form-encoded `grant_type=refresh_token`, `client_id`, `client_secret` and `refresh_token` POSTed to `https://api.amazon.com/auth/o2/token`. This matches the spec `tokenUrl` and the Postman `token_url`.
- `invalid_grant` is classified as Unauthorized.
- `validate()` does a fast-fail `GET /dsp/advertisers?startIndex=0&count=1`. Note that this validation endpoint is itself on the legacy surface (#3). If it is sunset, **every session will fail at establishment**, so it should move to `/v2/profiles` or a v1 endpoint as soon as possible.
- The access-token adapter memoizes `validate()`. The refresh adapter re-validates on each call, but it is only invoked once per session.
