# pinterest-mcp review

## Summary

The package is in poor shape where it touches the platform. The scaffolding follows repo conventions: tool registration, governance annotations, session services, account scoping and the auth fast-fail all match. The Pinterest-specific layer, though, looks copied from `tiktok-mcp` and never reconciled with Pinterest API v5. I checked it against Pinterest's official OpenAPI spec (v5.28.0, fetched live from `raw.githubusercontent.com/pinterest/api-description/main/v5/openapi.json`). The repo's own `src/generated/types.ts` already has the correct shapes and paths; the handlers just don't use them.

Top issues:
1. **`get_entity` returns the wrong entity** for campaign/adGroup/ad. It lists the entities with an `id` query param the API does not support, then takes the first item. Everything built on it inherits the bug: `duplicate_entity` clones the wrong campaign, `adjust_bids` reads the wrong previous bid, and `update_entity` takes its `before` snapshot and dry-run from the wrong entity.
2. **Batch writes report success on rejected items.** Pinterest batch create/update responses are `{items:[{data, exceptions}]}` and return HTTP 200 even when some items are rejected. The code treats `items[0]` as the entity, so rejected writes count as successes and created IDs are lost.
3. **Seven tools call endpoints or shapes that do not exist.** `delete_entity` sends DELETE to campaigns/ad_groups/ads, which have no DELETE method. The targeting, audience-sizing and ad-preview paths are wrong. Reports send `type` instead of `level` and don't set `report_format` (the default is JSON, but the code parses CSV). Video upload polls a field that doesn't exist, so it always waits the full 10 minutes. `adjust_bids` writes currency amounts into `bid_in_micro_currency`, so bids end up 1,000,000× too low.

**`retryNonIdempotent` question:** the opt-in sits in `postMultipart`, which nothing calls. It never runs, so the CLAUDE.md operational-envelope row describes behaviour that doesn't happen.

**Doc reachability:** `developers.pinterest.com` (API reference and changelog) and `community.pinterest.biz` are blocked by the egress proxy. The official OpenAPI spec (raw GitHub) and github.com releases are reachable, so the findings below that are marked "live-doc" were checked against Pinterest's published spec. Anything that depends on the prose docs is marked UNVERIFIED.

## Open questions

1. **Is ARCHIVED terminal on Pinterest?** From model knowledge, archived campaigns, ad groups and ads cannot be un-archived. If so, `bulk_update_status` / `update_entity` with `status: ARCHIVED` are irreversible and belong in `terminalOperations` (only `delete_entity` is listed today). This matters more once `delete_entity` is reimplemented as an archive. I couldn't confirm it because developers.pinterest.com is blocked.
2. What does the v5 API do with unknown query params like `id=`: ignore them (returning the wrong entity, the most likely case) or 400? Either way #1 is broken; the difference is whether it fails silently or loudly.
3. Is `level` required server-side in practice for async reports, even though the spec's `required` list omits it? The docs host is blocked.
4. Does refreshing a continuous refresh token invalidate the previous refresh token? If yes, #12's in-memory-only rotation becomes a hard outage after the first restart.
5. Rate limits: the default of 10/min is "platform_quota / 10 instances", but the Pinterest per-category ads rate limits could not be checked (docs host blocked). The only rate limit in the spec is 5,000/min per ad account on the conversions endpoint.
6. The GitHub release notes list new objectives (e.g. AD_RECALL_LIFT, BRAND_AWARENESS, VIDEO_VIEWS_10S/15S in v5.20.0) that are not in the spec's `CampaignCreateItem.objective_type` enum. Which is authoritative can't be resolved without the reference docs.
7. New capabilities not covered (low priority): targeting templates, `bid_floor`, `campaigns/delivery_estimates`, synchronous analytics (`campaigns|ad_groups|ads/analytics`), `targeting_analytics`, MMM reports, the sandbox (`/ad_accounts/{id}/sandbox`), and `continuous_refresh`.
