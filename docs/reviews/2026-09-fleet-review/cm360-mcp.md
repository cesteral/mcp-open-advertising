# cm360-mcp review

## Summary

Overall the package is structurally sound. All 21 tool files are registered, plus the generated `cm360_search_tools`. Every tool name has the platform prefix, governance blocks are present on all writes, and registry.json, the root README and allTools agree on 22 tools. Every endpoint path the package calls exists in the live CM360 **v5** discovery document (revision 20260721). The pinned `dfareporting/v5` is current: the discovery directory marks v5 `preferred: true`, and v4 and v6 discovery both return 404.

The main problems are in behaviour, not in paths. Top 3 issues:

1. **`cm360_download_report` sends the session's Google OAuth bearer token to any URL the caller supplies.** It has no host allowlist; ttd-mcp has one.
2. **The CM360 rate limiter does nothing.** Every call consumes the key `"cm360"`, but the limiter is configured for the pattern `"cm360:*"`, which that key does not match. The server card still publishes a 5/min limit.
3. **`update_entity` and `bulk_update_entities` send a PUT, which replaces the whole resource, with whatever partial object the caller gives.** The governed dry-run predicts a shallow merge instead, and the tool's own examples use partial payloads. v5 has `PATCH ?id=` for all 8 entity types.

Doc reachability: `developers.google.com` (release notes, deprecation schedule, REST reference) and `ads-developers.googleblog.com` are both EGRESS_BLOCKED. Accuracy checks therefore rely on the **live, machine-readable v5 discovery document** at `dfareporting.googleapis.com/$discovery/rest?version=v5`, which is reachable, plus web-search snippets. I could not read v5's sunset date.

## Accuracy notes (Part B)

- **Version**: v5 is the latest published version. Discovery marks v5 preferred, v4 and v6 return 404, and web snippets say v4 sunset on 2026-02-26. I could not read v5's own deprecation or sunset date (blocked host). platform-facts `cm360.api_version` (`codeRefs` `config/index.ts:20` ✓ still matches) is correctly left `unverified`. A reviewer could cite the reachable discovery directory as a secondary, machine-checkable source. It does not prove supported status, because it still lists v3.5.
- **Generated types** (`src/generated/types.ts`) contain `euPoliticalAdsDeclaration`, so they come from a recent v5 revision ✓.
- **CLAUDE.md Server-Specific note** ("profileId required on all calls, list_user_profiles for discovery, list_targeting_options, create/list/delete_report_schedule") matches the code and the discovery paths ✓. The one exception is `download_report`, which takes a URL rather than a profileId, as noted in #1.
- **New v5 capabilities not covered** (low priority): `reportData.query` (`POST userprofiles/{profileId}/reportdata/query`) is a synchronous ad-hoc query that returns JSON; it would replace the create→run→poll→download CSV path for small reports, and the Aug-2026 Google blog is about it. Also Dynamic Profiles/Feeds (`studio/dynamicProfiles`, `studio/dynamicFeeds`), `euPoliticalAdsDeclaration` on Campaign/Advertiser (passable via `data` but undocumented), `placements.generatetags`, `floodlightActivities.generatetag`, `reports.compatibleFields.query` (would let the tool check dimension/metric names), and `*.patch` for all entity types.

## Open questions

1. What `Content-Type` does `reports.files.get?alt=media` return for a CSV file? If it is `application/octet-stream`, finding #10 becomes high, because every download would be rejected. A live run is needed.
2. Does dfareporting v5 return 400 for unknown query parameters (e.g. `maxResults` on `metros.list`), or ignore them? This decides whether #5 and #16 cause errors or are cosmetic.
3. What exactly does a partial PUT do on `campaigns.update` / `ads.update`: 400 on missing required fields, or silent reset of omitted optional fields? Either way the dry-run is wrong (#3), but silent reset would be critical.
4. Can `reports.delete` delete another user's report when listed via `scope=ALL`? (#9)
5. The breakdowns description lists `device` as a common dimension; I suspect it is not a valid CM360 dimension name (`platformType` is), but this is from model knowledge and unverified. `floodlightImpressions` / `floodlightRevenue` metric names are likewise unverified. `reports.compatibleFields.query` could settle both.
6. `jwt` auth mode is advertised in registry.json, but `createSessionForAuth` returns a 400 "Use MCP_AUTH_MODE=google-headers" when there is no Google adapter. The same pattern exists in dbm-mcp and dv360-mcp, so this is fleet-wide and may be intentional (protocol-only sessions?).
7. Should `schedule.repeats` allow `QUARTERLY`/`YEARLY`? The v5 discovery field is a free string and its description documents only DAILY/WEEKLY/MONTHLY. Unverified.
