# dbm-mcp review

## Summary

`dbm-mcp` exposes 6 read-only DV360 reporting tools on the Bid Manager API through `googleapis` (`google.doubleclickbidmanager({version:"v2"})`). The endpoints it calls (`queries.create`, `queries.run`, `queries.reports.get`) match the **live v2 discovery document (revision 20260916)**. The OAuth scope is correct.

**v2 is still the current version.** It is the only `preferred` entry in Google's discovery directory, the v1.1 discovery doc now returns 404, and the newest `googleapis` npm release (182.0.0) ships nothing newer than v2. However, a **v3 discovery document is already served, but unlisted** (same revision). It is identical to v2 except that the sunset `FULL_PATH` and `PATH_ATTRIBUTION` report types are removed. That looks like a v3 in preparation. I found no v2 sunset date because the release-notes page is blocked.

Overall health is fair on the protocol surface and poor on runtime behaviour. Top 3 issues:

1. **`dbm_run_custom_query_async` cannot be used at all.** I tested this against the built server. The server has no task store and does not advertise the `tasks` capability. A task-augmented call returns `-32603 Server does not support task creation`, and a plain call returns `requires task augmentation`. Separately, even with a store the 5-minute task TTL is shorter than the default worst-case run time.
2. **The report retry loop retries every error.** That includes 400 invalid-query, 401/403, a reversed date range, and the local rate limiter. It makes 5 attempts with a 60 s cooldown between them. It re-sends the POST `create` and `run` calls. It finally throws a `Timeout`-coded `RetryExhaustedError` whose message drops the real cause. With default config one synchronous tool call can block for about 72 minutes.
3. **Several KPI and parsing outputs are likely wrong without any error:**
   - `granularity: weekly|monthly` returns an empty time series, because the parser only recognises `Date`/`Day` columns.
   - "ROAS" is computed as `METRIC_REVENUE_ADVERTISER / total media cost`. In DV360 that "revenue" is the amount billed to the advertiser, not conversion value (model knowledge).
   - Every call leaves a saved query behind in the user's DV360 account. The code never calls `queries.delete`.

**Doc reachability:** `developers.google.com`, `ads-developers.googleblog.com` and `ppc.land` are all blocked by the egress proxy. Google's live discovery endpoints (`doubleclickbidmanager.googleapis.com/$discovery`, `www.googleapis.com/discovery/v1/apis`) and the npm registry can be reached. Checks against the filters-metrics catalogue are therefore **UNVERIFIED**, apart from a few facts from search-result snippets, which are labelled as such.

## Open questions

1. Is v3 about to be announced, and will v2 get a sunset date? The v3 discovery doc is served but not listed and has no `googleapis` client. Someone with access to https://developers.google.com/bid-manager/release-notes should check.
2. Should pacing compare budget against Total Media Cost or against Revenue / billable cost? DV360 IO budgets may be spent against the partner revenue model, depending on configuration (model knowledge, not verified). This should be decided together with #4.
3. The real CSV header texts for Week/Month/Revenue and the Date format (#3, #18) should be confirmed from one real report. A sanitized sample would settle #3, #6 and #18 together.
4. Does Bid Manager limit the number of saved queries per user? If so, #5 becomes a hard failure over time rather than clutter. Unknown.
5. Does the shared tool factory pass a request AbortSignal in `sdkContext`? If it does, dbm should thread it into `pollUntilComplete`.
