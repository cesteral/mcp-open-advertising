# dv360-mcp review

## Summary

The package is structurally sound. There are 25 production tools plus `dv360_search_tools`, and every one is registered in `allTools`. Tool names are consistently prefixed, the session-services, retry and governance wiring follow fleet conventions, and the generated Zod entity schemas match the **live v4 Discovery doc (rev 20260923)** almost exactly. The only drift is 21 new `GeoRegionType` values and `SDF_VERSION_10_1`. The rev-20260608 removal of campaign and insertion-order assigned targeting **is correctly reflected**: `TARGETING_PARENT_TYPES` now holds only advertiser, lineItem and adGroup, and Discovery confirms that no `campaigns/*/targetingTypes` or `insertionOrders/*/targetingTypes` paths exist in v2, v3 or v4. v4 is still the `preferred: true` version in Google's API directory. A v5 Discovery doc now resolves, but it only contains SDF operation stubs.

The problems are concentrated in the "specialized" tools and in platform semantics that the code and CLAUDE.md state incorrectly:
1. **`dv360_duplicate_entity` is broken or unsafe.** Every insertion-order copy is forced to `ENTITY_STATUS_PAUSED`, but Discovery says `CreateInsertionOrder` accepts **only `ENTITY_STATUS_DRAFT`**, so every IO duplicate should fail. Line-item copies are GET→POST and **silently drop all assigned targeting**, even though a native `lineItems:duplicate` exists in v4. The claim "no native duplicate" is repeated in the service, the prompt and CLAUDE.md.
2. **Three tools call endpoints or fields that do not exist in v4.** `get_delivery_estimate` without a `lineItemId` calls `lineItems:generateDefault`, which is absent from v2, v3 and v4 Discovery. `get_ad_preview` reads `creative.previewUrl`, which is not a Creative field in v3 or v4, so it always returns undefined. The custom-bidding rules parser expects `CONSTRAINT_VIOLATION`, but the API value is `CONSTRAINT_VIOLATION_ERROR`, so parsing throws.
3. **The default rate limit of 6 req/min per advertiser throws, it does not queue.** The bulk tools advertise up to 50 items, but a bulk status change costs 2 tokens per item, so only about 3 items succeed and the rest fail. The README says the default is 60/min.

On delete semantics: Discovery says campaigns, IOs, line items and creatives "should be archived first", but the tool and its dry-run check this only for line items. The delete tool advertises delete for three types that have no DELETE method. Advertiser delete cascades irreversibly to all children, and nothing says so.

**Doc reachability:** `developers.google.com`, `ads-developers.googleblog.com` and `support.google.com` are all EGRESS_BLOCKED. The **Discovery docs at `displayvideo.googleapis.com` were reachable**, as was the `www.googleapis.com` API directory. Those are the machine-readable official reference, and most accuracy claims below are verified against them. Release-note and sunset claims come from web-search snippets only and are marked accordingly.

## Open questions

1. Is ARCHIVED really irreversible via the API? Discovery states no such restriction; it only forbids returning IOs and LIs to DRAFT. The claim sits in registry.json, CLAUDE.md, platform-facts and the tool descriptions with no source. A live test on a sandbox advertiser would settle it.
